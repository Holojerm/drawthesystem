# Interviewer notes (hidden)
Crux: content-defined chunking (rolling hash, not fixed-size blocks) so a small edit in the middle of a large file only changes the chunks around it, not everything after the edit point; a per-file version vector or last-writer-plus-conflict-copy model (never silent overwrite) for the offline-edit-collision case, matching what real sync products actually do (keep both, surface a "conflicted copy").
Probes: why fixed-size chunking breaks under a small mid-file insertion (every subsequent chunk boundary shifts) versus content-defined chunking; how a device offline for weeks figures out what changed without a full directory walk-and-compare against the server; what happens the instant both offline devices reconnect with conflicting edits to the same file.
Red flags: re-uploading the whole file on every edit ("it's simpler"); fixed-size block chunking presented with no awareness of the shifting-boundary problem; last-write-wins with silent data loss for the offline-conflict case.
